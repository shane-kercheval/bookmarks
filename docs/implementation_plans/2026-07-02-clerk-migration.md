## Context & Goals

Tiddly authenticates via Auth0 (web SPA tokens + CLI device flow) and app-managed Personal Access Tokens (`bm_` prefix). We are migrating the identity provider to Clerk. Beta scale (a handful of users) but **real user data that must not be lost** — content is keyed to internal UUIDv7 `users.id`, which never changes; only the identity *linkage* migrates.

### Why Clerk?

The short version, for readers who won't read the full capability ledger (`docs/auth0-clerk-ledger.md` — the blunt entry-by-entry comparison, with provenance). Two drivers headline: the migration **unlocks MCP OAuth** (goal 3 — the biggest currently-blocked feature), and it **deletes code and buys capabilities Tiddly would otherwise have to build**.

| What we gain | Why it matters |
|---|---|
| **End-user account self-service** (M3/M8) | Clerk ships `<UserProfile />` (password change, sessions/devices, account deletion). Auth0 ships no end-user account UI — which is why Tiddly never had one. Users gain capabilities that never justified hand-building. |
| **Extension signs in with the web app** (M7) | Clerk's Sync Host gives the Chrome extension the web session automatically — install it while signed in to tiddly.me and it just works; signed out, signing back in on the web is the remedy. No new user touches a PAT. The PAT option stays only as an escape hatch for the free tier's weekly session expiry (which otherwise surfaces at bookmark-save moments) and because removal would churn users who chose PATs — it's a candidate to retire once the Pro upgrade lengthens sessions. No comparably easy Auth0 equivalent existed. |
| **MCP OAuth for AI connectors** (M5) | ChatGPT and Claude Desktop native connectors *require* OAuth with dynamic client registration — each connecting AI client registers itself as an OAuth application in the provider. Mechanically this is comparable effort on either provider; the blocker is Auth0's free-tier cap of 10 total applications, shared with our own first-party apps. Registration granularity is the *client's* choice, not ours — observed ecosystem behavior ranges from one registration per platform to per-user/per-install, plus re-registration whenever a client loses its stored credentials (the unbounded growth that motivated the MCP spec's Client ID Metadata Documents proposal, Appendix A). Betting a user-facing feature on every third-party client staying under ~7 spare slots forever is a structural mismatch. Clerk supports DCR on the free tier (OAuth Applications confirmed free-tier; Clerk *documents* no cap on OAuth applications or DCR-registered clients — ledger question 4, answered from docs 2026-07-15: no documented limit analogous to Auth0's cap, though undocumented safeguards may still apply, and registration-endpoint abuse stays an operational risk M5's security review owns, distinct from the forced consent screen), issues JWT access tokens by default (which our networkless backend verification requires), and publishes first-class MCP-server guidance. |
| **Delete the client token machinery** (M3, iOS later) | Clerk's ~60s session tokens are auto-refreshed by its JS — the web frontend's detect-expiry/refresh/retry/dedupe choreography is permanently deleted, and an idle-overnight tab transparently gets a fresh token instead of the expired-cached-token dance. The iOS app gets the same deletion on its own timeline (ClerkKit owns the session and refresh; the hand-rolled Auth0 token bookkeeping goes away). Backend verification is unchanged either way. |
| **Better token security posture** | A stolen 60-second token is nearly worthless, and "sign out everywhere" takes full effect within about a minute — versus hours-long exposure with Auth0's long-lived tokens. |
| **Less auth machinery overall** | Custom claims are two config lines instead of a deployed Auth0 Action + namespace env vars; account linking happens inside the provider (one user, many login methods), which obsoleted a planned `user_identities` table; login UI is embedded components instead of a hosted redirect page. |
| **Future options this opens** (not built in this migration) | Organizations/teams for the roadmap (basic orgs free up to 20 members, prebuilt UI, org context in the session token, self-serve SSO/SCIM at the enterprise tier); billing via Clerk Billing when the product is ready to charge; MFA and passkeys as a dashboard action once on the Pro plan; Clerk API Keys as a candidate to replace the homegrown PAT system (AD1 — post-migration spike). |

**Costs, accepted knowingly** (detailed in the ledger and Known limitations): the free tier's fixed 7-day session lifetime (weekly re-login until the Pro upgrade); web sessions surviving a provider outage for only about a minute versus hours of coasting on long-lived tokens; and — a deliberately narrow one — no OAuth device flow, which affects **only browserless terminals** (SSH into a remote machine, headless environments), where PATs remain the supported path. Ordinary desktop `tiddly login` is *not* hindered — it actually gets smoother: the browser opens and you click sign-in, with no device code to read from the terminal and retype.

Goals, in priority order:

1. Migrate all users (email/password + Google social) to Clerk with zero data loss and passwords preserved.
2. End state looks as if Clerk had been implemented from the start — **no Auth0 residue in code, config, or schema**, and provider-specific shape contained to a narrow seam (see Architecture Decisions).
3. Ship MCP OAuth (Appendix A) as part of the migration — unlocks ChatGPT and Claude Desktop native connectors.
4. Maintain a capability ledger documenting Auth0↔Clerk functional differences discovered during the work.
5. **Adopt, not just migrate**: the end state should include the capabilities a from-scratch Clerk build would obviously have (see "Adoption decisions" below) — this plan's charter is migrate *and* adopt. Deliberate exception: billing — the product isn't ready to charge, and nothing here forecloses it.

## Architecture Decisions (locked — do not relitigate during implementation)

These decisions came out of design discussion and cannot be recovered from the codebase. Each must survive into the code as comments/docstrings at the relevant seam, or into the ledger — not evaporate during implementation.

**AD1 — PATs stay app-managed through this migration; Clerk API Keys are a post-migration candidate.** The `bm_` token system (`services/token_service.py`, `models/api_token.py`) is untouched. PATs are the auth path for clients that can't or don't use OAuth: headless CLI, Chrome extension, scripts, non-OAuth MCP clients. Clerk's API Keys product (GA 2026-04) is the direct managed equivalent, and the long-term principle — offload credential storage, hashing, and leak-handling to the vendor — is sound. Adopting it *here* is rejected on sequencing and neutrality, not product quality: it would force every user to re-issue tokens (extension, scripts, MCP configs) inside an already-large migration, and it would forfeit the migration's cheapest de-risking property — PATs are the one auth surface crossing the cutover with zero churn, precisely because they are provider-neutral (the same neutrality would spare a future provider move). Arguments deliberately NOT relied on (first-pass reasoning, corrected on review — record in the ledger): per-verification metering is negligible at any plausible scale (~$10 per million requests); PAT traffic is not clearly the hottest path and shrinks after M5 moves OAuth-capable MCP clients off PATs; and the outage-resilience gap vs Clerk-issued JWTs (day-lived, verified locally against cached JWKS) is narrow — it matters only if API-key verification requires a live Clerk call, which is unverified. Post-migration follow-up: spike that verification model, per-user key caps, and what the verified payload exposes for the audit trail; if clean, replacing `token_service.py` with Clerk API Keys is a legitimate delete-owned-security-code simplification.

**AD2 — No `user_identities` table; one provider-neutral column.** `docs/implementation_plans/future-identities.md` planned a multi-identity table because Auth0 surfaces each login method as a distinct `sub`. Clerk performs account linking *inside the provider* (one Clerk user, many auth methods, one stable `user_id`), which obsoletes that plan. End state: `users.external_auth_id` (unique, indexed) storing the Clerk user ID — a neutral *name* ("the `sub` claim of verified IdP tokens") with a provider-specific *value*, which is unavoidable. Never parse or derive meaning from its format. `future-identities.md` gets a superseded-by note.

**AD3 — Divergence from Clerk's migration guide: no `external_id` session-token aliasing.** Clerk's guide suggests customizing the session token to emit `{{user.external_id || user.id}}` so backends can keep keying on old Auth0 subs indefinitely. That pattern exists for large userbases with untouchable code. We reject it: we control the backend and have a handful of users, so we do a clean lookup-column swap instead. The old Auth0 `sub` IS stored in Clerk's `external_id` at import time — but purely as an audit breadcrumb inside Clerk. **The application never reads `external_id`.**

**AD4 — Divergence from Clerk's migration guide: no trickle migration.** Clerk documents running both providers in parallel and migrating users on activity. At our scale this is machinery without payoff. We do: bulk import → backend dual-accept window → single coordinated client flip → soak → decommission.

**AD5 — Cutover = backend dual-accept, single frontend/CLI flip.** During the transition window the backend verifies JWTs from *both* issuers (routing on the token's `iss` claim); both paths resolve to the same `users.id` row (Auth0 tokens via `auth0_id`, Clerk tokens via `external_auth_id`), so a user mid-transition (web on Clerk, CLI on a lingering Auth0 refresh token) sees one consistent account. The two columns coexist **only** during this window; the decommission (M6b) drops `auth0_id`. The window deliberately spans the iOS app's independent migration: M6a flips **web and CLI** to Clerk in production (existing MCP integrations keep working on Tiddly's own PATs — MCP *OAuth* connectors are M5, post-cutover) while iOS keeps authenticating via Auth0; M6b is gated on the iOS update shipping. Two window rules follow: (1) the production import must be complete before the first production Clerk login — an unimported user would JIT into a fresh, empty account; (2) no new Auth0 identities may be created once sign-up moves to Clerk — otherwise the same person can end up with two unlinked accounts (one per provider). Both rules are enforced in the backend, not only at the provider edges — M1's per-issuer JIT-create flags make any leak through a dashboard setting a loud 401-plus-log instead of a silently created account. A third window property, accepted and recorded: **no Clerk-side security control constrains the Auth0 issuer while the window lives** — "sign out everywhere", and any future control like MFA, bind only Clerk's own sign-in ceremony; account deletion is the one deliberate exception, backstopped app-side by M8's tombstones. Such controls gain their full effect at M6b.

**AD6 — Neutral naming at the small leaks.** `AuthType.AUTH0` → `AuthType.SESSION` (mechanism-descriptive, covers both issuers during dual-accept; a future provider swap doesn't touch it). Redis auth-cache key segment `auth:vN:user:auth0:{id}` → `auth:vN:user:ext:{id}` with a schema-version bump. Historical `content_history.auth_type` rows keep the literal `"auth0"` — audit rows describe what was true at the time; do not backfill.

**AD7 — Backend verifies Clerk session tokens with the existing PyJWT/JWKS pattern, not the Clerk SDK, on the hot path.** Clerk session tokens are standard RS256 JWTs verified against a JWKS endpoint — the same shape `core/auth.py::decode_jwt` already handles. Key differences from Auth0: tokens are short-lived (~60s, auto-refreshed by clerk-js) and carry **no audience**; the equivalent check is `azp` (authorized party) against an allowlist of our web origins. The official `clerk-backend-api` Python SDK is used only where the Backend API is genuinely needed (the import script in M2). Rationale: consistency with existing code, no new dependency on the request path, and token *verification* never depends on Clerk being reachable — during a Clerk outage, day-lived OAuth tokens and PATs keep working; web sessions still end within about a minute when token re-issuance stops (see Known limitations and the ledger's Reliability entry).

**AD8 — Auth cache keys on `sub`, not on raw token.** Already true today (cache is keyed by `auth0_id`/`user_id`, not token) — preserve this. With 60-second Clerk tokens, any token-keyed cache would be useless; the sub-keyed design is why the 5-min TTL survives the migration unchanged.

**AD9 — CLI: device flow → authorization code + PKCE with loopback callback; PATs are the headless story.** Clerk does not support RFC 8628 device authorization (verified against OAuth server metadata, Clerk's own CLI-auth blog, and their public roadmap where it is backlog-only). The replacement is the `gh auth login` pattern: ephemeral listener on `127.0.0.1`, browser to Clerk's `/oauth/authorize` with PKCE (S256), code exchange at `/oauth/token`, tokens in the OS keyring. This loses true remote/SSH interactive login (browser must run on the same machine as the CLI); the documented fallback is `tiddly login --token bm_...`, which already works and does not change.

**AD10 — MCP servers stay thin bearer-passthrough proxies.** MCP OAuth is implemented exactly as sketched in Appendix A, with Clerk substituted for Auth0 as the authorization server: each MCP server adds one static discovery endpoint (`/.well-known/oauth-protected-resource`) pointing at Clerk; Clerk handles DCR, login, consent, and token issuance; the MCP servers keep forwarding whatever bearer arrives; the **backend API** is the only component that verifies tokens. Bearer/PAT auth remains supported (a must-have requirement — Appendix A).

**AD11 — Capability ledger.** `docs/auth0-clerk-ledger.md` is a living document, seeded in M0 and updated in every milestone's Definition of Done. Entry shape: capability · how Auth0 does it · how Clerk does it · what migrating took · gained/lost/neutral · gotchas (including "possible on both, but…" nuances and divergences from Clerk's own guides, per AD3/AD4). This is the raw material for a later external writeup; be blunt in it.

## Adoption decisions (the migrate-and-adopt register)

Capabilities Clerk makes cheap that Tiddly never built (or chose differently). Each gets an explicit status here so nothing sits as an ambiguous "if." Tier facts verified against clerk.com/pricing (2026-07): the free (Hobby) tier lacks MFA, passkeys, and branding removal, and fixes session lifetime at 7 days; Pro is $25/month.

| Capability | Decision | Notes |
|---|---|---|
| Account deletion | **Adopt — M8** | Immediate hard-delete. Rationale: deletion starts in Clerk's UI, so the identity is gone before our webhook fires — a "log back in to cancel" grace period is impossible without owning the whole flow ourselves, which defeats using the free component. Clerk's component owns the confirmation UX; content-level trash (soft-delete + 30-day sweep) is unaffected. |
| MFA | **Deferred — rides the Pro upgrade** | Pro-gated, so it defers with the plan-tier decision below. When Pro happens, adoption is near-zero-cost: enforcement runs inside Clerk's sign-in ceremony (backend untouched) and enrollment UI ships in `<UserProfile />`. Deferring also dissolves the "Clerk-side MFA doesn't bind the Auth0 issuer during the window" concern — no MFA ships during the window at all. |
| Clerk plan tier | **DECIDED 2026-07-06: Free at cutover; upgrade to Pro when the product has real users** | Trade accepted knowingly, on verified facts: the free tier fixes sessions at a 7-day **absolute** lifetime — every active user re-logs-in weekly, possibly mid-session, and the expiry propagates to the extension's synced session (M7) and iOS — a genuine regression versus Auth0's default 30-day **inactivity** sessions, under which active users were never logged out. Also: "Secured by Clerk" branding stays. Judged not worth $300/yr for a handful of beta users; documented as a regression in the ledger; the cutover email sets expectations. Upgrade trigger: paying users or meaningful growth — the upgrade is a dashboard action plus enabling MFA, no code. |
| Opaque tokens for the MCP path | **Declined — JWT kept (AD7)** | Agents are the chattiest clients; per-request verification calls add latency and couple the agent path to Clerk availability. Narrow the revocation window via OAuth token lifetime (spike Q2) instead; the blunt emergency fallback (revoke the grant and sessions) always works. Revisit only on real agent abuse. |
| Passkeys | **Deferred** | Pro-tier; solves a problem we don't have (one password user + Google). Can be enabled later with no architectural consequence. |
| Authorized-apps management UI | **Rides open question 12** | Free if `<UserProfile />` includes it; else a small post-M5 build against Clerk's API. |
| Billing (Clerk Billing / Stripe) | **Deferred — product readiness** | The charter's stated exception; deliberately decoupled (plus the open VAT/refunds questions). |
| Legal consent (ToS/privacy) via Clerk | **Post-migration spike — ledger Q17** | Clerk ships a "Require express consent to legal documents" instance setting (sign-up checkbox + ToS/privacy URLs, spotted 2026-07-12). Tiddly's consent system is substantially bigger than a sign-up checkbox: versioned policies, re-consent on version bump enforced backend-side (451) across every client including MCP/CLI, and an auditable `user_consents` record. The spike (post-migration, so it can't scope-creep the cutover): does Clerk track acceptance queryably (`legal_accepted_at`), can it represent *new versions* requiring re-consent, and can it enforce anywhere beyond the sign-up ceremony? If it can't do version-bump re-consent + API-side enforcement, it complements but cannot replace our system. |
| Orgs / B2B | **Deferred — ledger Q13** | Newly verified: basic organizations up to 20 members are free on all plans; $100/month is the *enhanced* add-on. Relevant when teams reach the roadmap. |

## Operator steps — human-only, or agent-run with human approval

Flagged inline per milestone, collected here so nothing blocks silently. **Policy (set 2026-07-06, after M0 showed the Clerk CLI can drive nearly all instance setup):** the agent does whatever it can — we do *not* push manual work onto a human that a command can do. But before running any Clerk command that *changes* state (`config patch/put`, `apps create`, `enable`, `deploy`, …), the agent first shows the human the exact command(s) and the reason, and waits for approval; read-only commands (`clerk config pull`/`schema`, `whoami`) just run. Production mutations are included in this approval gate — approval, not manual execution, is the control. So the steps below fall into two kinds:
- **Genuinely human-only** (outside Clerk, no command exists): registrar DNS records, Google Cloud Console OAuth-credential creation, sending the cutover email, and the one-time `clerk auth login` browser sign-in.
- **Agent-run with show-and-approve** (Clerk CLI mutations, dev and prod alike): the agent proposes the exact command, the human approves, the agent runs it.

Each milestone's list below is re-triaged into these two kinds as that milestone is reached (M0 was done this way); items are not pre-classified speculatively.

## Release choreography — what merges vs what ships (M3 → M6a)

Railway auto-deploys `main` to production, and M3/M4 are code-complete weeks before the M6a flip. Without an explicit rule, an implementing agent who finishes M3 and merges it (the normal thing to do) takes production down: the deployed frontend either falls back into dev mode (missing Clerk key → `isDevMode` → sends no credentials → every request 401s) or presents a Clerk login against an instance containing zero production accounts. Merging is not shipping — per component:

- **Backend and MCP servers: merge and deploy continuously.** They are production-safe by design at every milestone — M1's dual-accept keeps Auth0 working, and M5's gate is presence-only. No holds.
- **Frontend: the flip branch is held unmerged; `main` keeps deploying normally.** (Revised 2026-07-12 — operator decision, replacing the original "merge M3, pin the Railway frontend service to a frozen branch" choreography.) The M3 flip PR stays an open, unmerged branch until M6a's flip step merges it — the merge itself is the deploy trigger, and Railway configuration is never touched. Rationale: no hidden deploy state in the Railway dashboard, and a production frontend hotfix during the window lands on `main` and ships immediately, exactly as today (under the pin it needed a cherry-pick to the frozen branch). Costs accepted with eyes open: the flip branch periodically absorbs `main` (solo-repo, conflicts limited to docs and shared frontend files touched by later milestones), and cutover day includes the merge itself rather than only a dashboard flip. M6a's rollback target is a revert of that flip merge on `main` — Railway redeploys the Auth0 frontend.
- **CLI: code merges freely; the binary *release* is an M6a flip step.** Publishing the M4 binary early would log out every user who upgrades, into a login with no production account behind it.
- **Chrome extension: already handled** — M7 states store publish happens only after M6a (the review that found this gap noted the extension was the only client of three that had the treatment; this section extends it to the other two).

Rejected alternative: a build-time "both providers" frontend flag. It would force keeping both auth SDKs and testing both paths through the whole window, contradicting M3's clean-removal design (step 5) for no benefit over a deploy hold.

### PR structure — one PR per milestone, with deliberate exceptions

Completing a milestone (Definition of Done passed, review done) ends with opening its PR — the review boundary and the merge boundary coincide. The default is one PR per milestone; the exceptions:

- **M3 is two PRs**: step 0's seam refactor merges first, against Auth0 (as step 0 already requires — a pure refactor that shrinks the risky diff); the Clerk SDK swap and the rest of M3 are the second PR, which is opened for review when code-complete but **stays unmerged until M6a's flip** (per above).
- **M4 is two PRs**: the backend OAuth-access-token acceptance (the piece M5 depends on) separate from the Go CLI rewrite — different languages, different verify gates (`backend-verify` vs `cli-verify`), and the backend half deploys on merge while the CLI binary release is held.
- **M8 is one PR merged before M6a** — its deletion backend is an M6a prerequisite. Milestone numbers are narrative order, not merge order; the dependency graph drives merging.
- **M6a has little or no PR of its own** — it is operational (env-var flips, merging the held M3 flip PR, import run, CLI release, cutover email), not a change-set.
- Docs/config-only work (plan, ledger, `clerk/config.dev.json` re-pulls) merges as its own PR whenever coherent.

This granularity is load-bearing, not taste: coherent single-milestone PRs are the **abandonment mechanism**. Until M6b — the plan's only one-way door — "roll back the Clerk work entirely" is a `git revert` of a short, known list of PRs plus one down-migration, because nothing before M6b touches anything Auth0 depends on: rollback is trivial through M1–M4 (production runs on Auth0 throughout these; the Clerk paths are dormant until tokens arrive), still recoverable at M6a (revert the flip merge on `main` — Railway redeploys the Auth0 frontend — re-enable Auth0 sign-ups and JIT-create — losing only window-era Clerk sign-ups and password changes; the import never modified Auth0), and gone only when M6b deliberately deletes the Auth0 path, column, and tenants after soak.

**Execution-order note.** Although numbered M5 then M6, **M5 (MCP OAuth) ships *after* the M6a cutover** — effective execution order **M6a → M5 → M6b** — because M5's OAuth connectors are only usable once users are in Clerk. So M5 runs *inside* the dual-accept window (production already Clerk-primary, Auth0 still accepted), **not** before cutover; the "production runs on Auth0 through M1–M4" framing above applies to the numbered pre-cutover milestones, not to M5's actual execution slot. M5's own rollback is the same continuous-deploy revert, just against a Clerk-primary production.

## Milestone 1 — Backend dual-accept

### Goal & Outcome

The backend verifies both Auth0 and Clerk JWTs, resolving both to the same user rows. Nothing user-visible changes; production keeps running on Auth0.

- A request bearing a valid Clerk session token authenticates, JIT-provisions a user on first sight (same semantics as today's Auth0 path), and passes consent/rate-limit checks identically.
- All existing Auth0-token and PAT behavior is unchanged and all existing tests pass.
- Every Auth0-path authentication emits a log line that includes the resolved request source (the cutover signal — during the M6a→M6b window, `ios` is expected to be the only remaining Auth0 source, so the log must distinguish clients).
- The schema has a nullable unique `users.external_auth_id` column, empty for now.

### Implementation Outline

Read `core/auth.py`, `core/config.py`, `core/auth_cache.py`, `core/request_context.py`, `schemas/cached_user.py` first — the entire provider seam lives there (keep it that way; that containment is AD-level intent, note it in the module docstring).

(Alembic autogenerate does not detect CHECK constraints — migration `5fd6c03a4e43` in this repo hand-adds one and is the template.) 3. **Token routing in `_authenticate_user`**: `bm_` prefix → PAT (unchanged). ## Milestone 2 — User import & backfill

### Goal & Outcome

Every existing Auth0 user exists in Clerk with working credentials, and every Postgres user row is linked to its Clerk user.

- The password user completes their first Clerk sign-in (email code — settled by the M2 rehearsal, ledger Q10) with **all data intact**. Password credentials are deliberately not preserved (the M0 no-hash-export decision); the cutover email says so.
- Google users are imported with their verified emails (carried from the export, not asserted — see the contract) so Clerk's account linking silently attaches their Google login on first sign-in; any unverified-email rows link with a verification prompt instead.
- Every imported Clerk user carries `external_id` = the old Auth0 `sub` (audit breadcrumb only, per AD3).
- `users.external_auth_id` is populated for every row; a verification report proves the mapping is total and 1:1.

### Implementation Outline

A one-off, idempotent Python script (location per repo conventions; it is repo code, typed and reviewed like any other) using `clerk-backend-api` (the one sanctioned SDK use, per AD7). Input: the Auth0 bulk user export (self-serve; operator supplies). Per the M0 decision, **no password-hash export is used**: the single password-based user is imported without a password via `skip_password_requirement: true` — permitted because password is not the instance's only sign-in method (Google is enabled; verified against the CreateUser reference) — and completes first sign-in via email code (settled by the M2 rehearsal — see "First sign-in experience" below).

Contract and edge cases decided in discussion:

- For each Auth0 user: create Clerk user with the primary email's verified status **carried through from the Auth0 export — not asserted** (verified emails are what make Google account-linking silent; but blanket-asserting verification would launder an unverified address into "verified," and the real owner of that address clicking "Sign in with Google" later would land silently inside an account someone else created — the classic pre-hijack shape; carrying the flag means genuinely-verified users still link silently while unverified ones get a verification prompt, exactly the right behavior for the suspicious case) and `external_id` = full Auth0 `sub` string. The dry-run report lists any unverified-email rows by name. **Footgun confirmed in the M0 spike: a Backend-API-created user gets its email marked `verified` by default** — the API will happily over-vouch, so the script must set verification *explicitly* from the export, never rely on the default. Password users (`auth0|` subs) get `skip_password_requirement: true` per the M0 decision (also confirmed working in the spike — a passwordless BAPI user was created cleanly); `google-oauth2|` users import email-only as they always would. (Clerk's bcrypt `password_digest` import path exists and is recorded in the ledger; it is deliberately unused here.)
- A user may appear in the export as *both* `auth0|` and `google-oauth2|` subs with the same email (Auth0 kept them as separate users unless linked). The dry-run **pre-classifies every email collision against Postgres** before any Clerk user is created: zero DB rows → log and skip; exactly one DB row → create one Clerk user mapped to that row (`external_id` = the sub stored in `users.auth0_id`), logging the discarded sub; **two or more DB rows → hard preflight failure naming the accounts** — one human with two data-bearing Tiddly accounts is a manual merge/ownership decision the script must never guess. (Note: the backfill's existing no-match hard-fail would already catch this case — the classification's value is making the failure *legible and early*, telling the operator which decision is pending, rather than an opaque unmatched-row error.)
- Backfill: match each `users.auth0_id` row to its created Clerk user, write `external_auth_id`. Any Postgres row without a match, or Clerk user without a row, is a **hard failure** printed in the report — never guess-match by email at write time.
- `--dry-run` prints the full intended mapping without writing to Clerk or Postgres. Idempotency: re-runs must not duplicate (look up by `external_id`/email before create). Handle Clerk 429s with backoff — don't crash mid-import.

**First sign-in experience for the imported password user** (this is what the M6a email describes; settled empirically in the M2 rehearsal — ledger Q10): their old password exists only inside Auth0, which nothing consults after the flip — their Clerk account starts with no password at all. The sign-in flow never shows a passwordless account a password prompt or a forgot-password link; with `email_code` enabled as a sign-in strategy (our config), entering their email goes straight to a six-digit code Clerk emails them — proving they can read that inbox *is* the identity check. First sign-in is enter email → enter code → signed in; the account stays passwordless unless they later choose to set a password (M3's account page). "Sign in with Google" also works instantly if they prefer it, because their email was imported as verified, so Clerk attaches the Google login to their existing account. Either way the account and all its data are untouched — same account, new credential. The application sends no emails for any of this; Clerk sends the codes itself.

Run order: dry-run against dev instance → real run against dev instance with a test export → (M6a cutover) real run against production instance.

### Definition of Done

- Unit tests for the export-parsing and collision/mapping logic (the API-calling shell can be thin and untested; the decision logic must be tested — this script is the single highest-data-risk artifact in the migration).
- Dev-instance end-to-end: import a fixture export; complete a no-password user's first sign-in (email code — the flow the rehearsal confirmed passwordless accounts get); sign in with Google on a verified-email user and confirm silent linking; confirm `external_auth_id` backfill.
- Verification report format finalized (counts: exported, created, skipped-as-duplicate, backfilled; must reconcile to zero discrepancy). The report also lists any **pre-existing Clerk users on the target instance that the export doesn't account for** — unexpected walk-in accounts are a hard failure unless explicitly named as operator/test accounts (see the M3 sign-up restriction).
- Unit test: the multi-row same-email collision classification (≥2 DB rows → hard preflight failure). Unit test: `email_verified` carry-through — a verified export row imports verified, an unverified row imports unverified (never asserted).
- **Security review (operational as much as code)**: custody of the user-export file and the Clerk secret key; the script must not log secrets or more PII than the reconciliation report needs. The M0 no-hash-export decision deleted this review's worst item — no password-hash file exists. (If the optional ticket is ever exercised, full hash-file custody rules apply: never logged anywhere including dry-run output, archival location named, every other copy deleted.)
- Ledger updated (hash-export friction, account-linking behavior, dual-sub collision handling).

## Milestone 3 — Frontend flip

### Goal & Outcome

The web app authenticates exclusively through Clerk. This milestone is code-complete and dev-instance-tested before any production flip (which happens in M6a).

- Sign-up, sign-in (email/password + Google), sign-out, and session persistence work through Clerk.
- Authenticated API calls carry a Clerk session token; the 401-retry-then-logout behavior is preserved under the new token model.
- Dev mode (`VITE_DEV_MODE`) still bypasses auth entirely, exactly as today.
- Consent (451) flow, protected routes, and the post-login return-to-origin redirect behave identically.
- **New capability, not parity**: users get a self-service account page (password change, security/session management) — functionality Tiddly never had, because Auth0 shipped no end-user account UI and building one never justified itself.
- **Session expiry never costs a user their work** (required outcome — the contract is step 7, backstopped by step 8's draft autosave): with the free tier's fixed 7-day session, expiry mid-edit is a weekly certainty for someone; the contract is that it can never lose an edit or navigate the user away from their note.

### Implementation Outline

A provider seam exists for auth *status* only (`AuthProvider.tsx` → `AuthStatusProvider` → `useAuthStatus()`). Auth *actions* and user-profile reads do NOT go through it: seven files import `useAuth0` directly for `loginWithRedirect`/`logout`/`user` — `PublicHeader.tsx`, `SaveACopy.tsx`, `SidebarUserSection.tsx`, `Pricing.tsx`, `LandingPage.tsx` (which also reads auth *status* off the SDK, `LandingPage.tsx:404` — the seam must carry status there too, not just actions), `FeaturesPage.tsx`, and `SettingsGeneral.tsx` (which also reads `user?.email` off the SDK object). The full seam is therefore a *target state this milestone builds*, not something that exists:

0. **First step**: extend the seam to cover actions + user fields (login/logout/email — whatever the seven call sites actually need, judged against their code), migrate all seven onto it, and enforce the boundary with an ESLint `no-restricted-imports` rule so only `AuthProvider.tsx` may import the auth-provider SDK — wired into `frontend-verify`, not a one-time check. This can (and should) be done and merged *against Auth0 first*, before the SDK swap — it's a pure refactor that shrinks the risky change.

1. Replace `@auth0/auth0-react` with `@clerk/clerk-react` in `AuthProvider.tsx`. Login/signup UI: use Clerk's prebuilt components/modal (we currently delegate UI to Auth0's hosted page; prebuilt Clerk components are the equivalent least-custom-code choice). `userId` comes from Clerk's user id (replaces `user?.sub`).
2. `config.ts`: `VITE_CLERK_PUBLISHABLE_KEY` replaces the three `VITE_AUTH0_*` values. Preserve the existing semantic that a missing key falls back to dev mode (`isDevMode`), including its test.
3. `services/api.tsx` interceptor: `getToken()` per request (clerk-js serves a cached ≤60s token and refreshes in the background — this *replaces* the Auth0 refresh-token machinery; there is no client-held refresh token anymore). The 401-retry path forces a fresh token (Clerk's skip-cache option) once, then falls to `onAuthError` → `signOut()` + the existing consent/queryClient cleanup. The shared-refresh-promise dedup may simplify or disappear — judge against the actual interceptor code, but the observable contract (one retry, then logout) must hold.
4. Post-login redirect: preserve the `toSafeReturnTo` sanitization on whatever Clerk's redirect-completion hook provides.
5. Keep the Auth0 npm package and env vars until M6b removes them repo-wide? **No** — this milestone removes the frontend's Auth0 dependency outright (the frontend can only speak one provider; dual-accept lives in the backend, per AD5). What M6b removes is the *backend* Auth0 path and deploy config.
6. Operator: production-instance DNS + Railway env vars are prepared here but the production flip itself is executed in M6a. **This milestone's flip PR must not merge until M6a** — merging auto-deploys it and takes production down (dev-mode fallback or a login against an empty instance). Per the Release choreography section (revised 2026-07-12), the branch is opened for review when code-complete, held unmerged through M4–M8, absorbs `main` after each interim merge, and is merged as M6a's flip step.
7. **Session-expiry UX contract (required — the free-tier 7-day session makes mid-edit expiry a routine event, and the current 401 handler would eat the edit).** The contract, stated as hard requirements the implementation must satisfy exactly:
   - On a 401 caused by session expiry: **no navigation, ever**. The current page — including the editor component and its in-memory content — never unmounts. Sign-in is presented **in place** as a modal overlay.
   - The Google button inside that modal uses Clerk's **popup OAuth flow** (`oauthFlow: "popup"` — verified supported; the default is "auto" and must be pinned, because a same-tab redirect would destroy the page and silently void this entire contract). Terminology, so no one conflates the two: the *modal* is our own in-page overlay component — browsers have no mechanism to block it; the *popup* is a real separate window (`window.open`) showing Google's sign-in page, necessary because Google forbids embedding its login page in another site's frame. Popup-blocker requirement: the popup must open **synchronously inside the click handler** — browsers (Safari strictest) allow `window.open` only when directly tied to a user gesture, and async work between the click and the open breaks that association and gets the window blocked. If a blocker fires anyway (broken gesture chain, aggressive third-party blocker): the no-navigation guarantee still holds unconditionally, and the step-8 draft covers the text — the user can reload and their work restores.
   - After successful re-auth, the **original failed request is retried automatically** — the save the user attempted completes; they are exactly where they were, with nothing to redo.
   - **No dismiss/escape path (revised 2026-07-12 from the live rehearsal; supersedes the original "dismiss → stay on the page, content copyable, persistent banner" requirement).** The dismiss path was found to be both unworkable and unnecessary: the app shell (`AppLayout`/`Layout`/sidebar) is entirely auth-and-data-gated, so "keep me on the page" rendered a blank shell, not the editor — and draft autosave (step 8) already guarantees the work is safe (persisted to localStorage, restored on reload) *regardless of the modal*, including if sign-in itself is broken. So the expiry modal has no dismiss control; re-auth is the single path forward, and the dialog says so ("your work is saved as a draft"). This still honors the original intent — never navigate away, never lose work — while deleting the banner/dismiss/reopen machinery and the impossible "render the dead shell usefully" burden. The mechanism the old clause guarded against (logout + redirect that discards everything) remains forbidden by the no-navigation rule above.
   - `queryClient.clear()` and consent-store reset run **only on deliberate logout** — never on the expiry path.
   - **Background loading indicators are suppressed while expired** (a body-level CSS class): parked requests hold widgets in their loading state, and a spinner animating behind the dimmed overlay reads as breakage, not waiting. Hidden (not unmounted, so no layout shift); everything resumes visibly on re-auth.
   - **Pre-expiry warning**: the expiry moment is deterministic and client-knowable (the session object's expiration); surface "your session expires soon — sign in again now" (banner/toast) ahead of it, so most re-auths happen at calm moments instead of mid-sentence.
8. **Draft autosave (required — independent scope, decided on its own merits, not part of the step-7 contract).** Step 7 fully handles session expiry on a live page; drafts protect against what no session-expiry UX can — the page dying with unsaved work in it: Cmd+W, Cmd+Q, browser crash, power loss. (After the step-7 revision above, drafts are also the *sole* rescue for the two cases the modal can't complete — a blocked re-auth popup, or a user who won't/can't sign in — which is what makes the dismiss-less modal safe.) Implementation: debounced localStorage write of in-progress editor content keyed per item (plus a key for unsaved new items); cleared on successful save; on opening an item with a lingering draft, a restore prompt ("Unsaved draft from N minutes ago — Restore / Discard"). Performance guardrail: serialize the editor content **only inside the debounced callback**, never per keystroke/change event — that debounce boundary is the entire difference between imperceptible and typing lag; at Tiddly note sizes the localStorage write itself is sub-millisecond and fires during typing pauses. Tiddly reportedly had draft-caching logic previously — check git history first; it may be resurrectable.
9. **Account-management settings page (new capability)**: mount Clerk's `<UserProfile />` as a settings page (Settings → Account) rather than linking out to the hosted Account Portal — same prebuilt UI, but users stay inside the app, consistent with the existing settings pattern (the portal link-out is the fallback if mounting has friction). **Guard rail**: per the M0 spike's section enumeration (ledger question 12), do NOT expose an account-deletion section unless deletion is properly wired end-to-end (Clerk `user.deleted` webhook → backend cascade delete) — a Clerk-side deletion without backend handling deletes the identity while orphaning all the user's data in Postgres. Hide or configure that section away until a real deletion story exists. Add the new page to `frontend/src/data/settingsRoutes.tsx` (command-palette search index, per AGENTS.md).

Edge case from discussion to verify explicitly: laptop-sleep / long-idle tab followed by an API call must transparently get a fresh token (this is a *behavioral improvement* over Auth0's expired-cached-token dance — confirm, and note in ledger).

### Definition of Done

## Milestone 5 — MCP OAuth (Appendix A)

### Goal & Outcome

MCP clients that require OAuth can connect to Tiddly's MCP servers with a paste-the-URL experience; bearer/PAT auth keeps working.

- Claude Desktop native Connectors and ChatGPT can add `https://<content-mcp>/mcp` and `https://<prompt-mcp>/mcp`, complete a browser sign-in, and use the tools.
- Existing bearer-token MCP configs (Claude Code, Codex, `tiddly mcp configure` output) keep working untouched.
- Unauthenticated MCP requests return 401 with the discovery metadata pointer, per spec, so OAuth-capable clients can bootstrap.

### Implementation Outline

Per AD10, the servers stay proxies; Appendix A's requirements are the shape. For each MCP server:

1. Serve the protected-resource metadata (static JSON: `resource` = that server's **full canonical `/mcp` endpoint URL** — per RFC 9728 §3.3 the `resource` must equal the URL clients connect to, which is `https://<host>/mcp`, *not* the bare origin — `authorization_servers` = [Clerk issuer, `https://<CLERK_FRONTEND_API>`], `bearer_methods_supported: ["header"]`). Each server states its own `resource` via a **service-specific, required env var** — **`CONTENT_MCP_RESOURCE_URL`** / **`PROMPT_MCP_RESOURCE_URL`** (not a shared name — avoids two processes reading one value in a shared `.env`), set to that server's own full `/mcp` endpoint. **Required in every environment** (local dev included, via `.env.example`); there is no localhost fallback, so a missing/malformed value crashes the server at startup rather than silently advertising a placeholder resource (config is validated once at import: absolute HTTPS-except-localhost, no userinfo/query/fragment, path exactly `/mcp`; `CLERK_FRONTEND_API` validated as a bare hostname). Add both to `.env.example` here, re-check in M6b's docs sweep, and have each server's metadata test assert its own served value against a literal. The metadata URL clients discover is the RFC-derived `…/.well-known/oauth-protected-resource/mcp` (well-known segment inserted between host and path); serve it there (canonical) and at the root path (compat fallback). Browser CORS (incl. `OPTIONS` preflight and exposing `WWW-Authenticate`) is handled by Starlette `CORSMiddleware` (outermost), the same pattern as `api/main.py`.
2. **This is new HTTP-layer auth gating, not a realignment — and it is the riskiest piece of M5.** Neither server rejects unauthenticated requests at the HTTP layer today: the content server fails at tool-invocation time (`_get_token` → FastMCP `ToolError`), and the prompt server's `AuthMiddleware` only *stages* the token into a contextvar, rejecting nothing. Add ASGI-level, pre-dispatch bearer checks to both: a missing `Authorization` header on the MCP endpoint → HTTP 401 with `WWW-Authenticate: Bearer resource_metadata="<metadata-url>"` (RFC 9728 §5 — this is what triggers client OAuth bootstrap) *before* any MCP/JSON-RPC handling. **Presence-only at the proxy**: a present-but-invalid bearer flows through and fails at the backend API, which remains the only verifier (AD10) — state this boundary in code. Existing bearer clients send the header on every request and never hit the gate; regression-test that explicitly rather than assuming it. Implementation specifics an agent would otherwise have to guess: the **content server needs an entrypoint change**, not just added middleware — it currently runs FastMCP directly; gaining an ASGI layer means serving via `http_app()` under uvicorn. The **prompt server's gate must cover both `/mcp` and `/mcp/{path}` routes across methods** (its routing splits them). And **`/health` stays public on both servers** — gating it breaks the deployed security tests and Railway health checks.
3. Testing-ladder checkpoint: if MCP Inspector / Claude Desktop / ChatGPT probe `/.well-known/oauth-authorization-server` on our origins (some older clients do), decide then whether to proxy/redirect it to Clerk's — don't build it speculatively.
4. Enable dynamic client registration on the Clerk instance — a CLI-patchable instance flag (`clerk api instance/oauth_application_settings -X PATCH -d '{"dynamic_oauth_client_registration": true}'`), so this is config-as-code like M0/M4, not a dashboard-only human step; the prod-secret custody stays with the operator, the flag flip does not. JWT token format was already confirmed instance-wide (ledger Q3, live 2026-07-13) and both settings are instance-level, so DCR clients inherit the JWT format by construction — re-verify on enable. **DCR client metering (ledger Q4) is answered from docs:** Clerk *documents* no cap on OAuth applications or DCR-registered clients and no registration-specific rate limit or tier gating — so no documented limit analogous to Auth0's hard 10-app free-tier cap (the concern this feature was partly motivated by) is known. This is documentation-based, not proof of absence: undocumented platform safeguards may still apply, and only Clerk Support could confirm otherwise (not worth pursuing pre-M5). On enable, validate one real DCR registration succeeds and watch for any immediate provider-imposed limit; treat any such limit as an **operational risk with a documented response** — inspect registrations, disable DCR via this same instance flag, remove abusive clients. - **MCP transport security (`Host`/`Origin`, DNS-rebinding).** The MCP SDK's DNS-rebinding protection is off by default (`enable_dns_rebinding_protection=False`); the bearer gate carries the live protection (an attacker's cross-origin JS holds no bearer — the token is not an ambient browser credential), so this is defense-in-depth, but the Streamable-HTTP spec *requires* `Origin` validation and the pattern must not be copied to the content server unhardened. **Implemented on the prompt server** (its own commit, before the content-server commit): `TransportSecuritySettings` enabled with `allowed_hosts` **derived from the canonicalized resource URL** (canonical authority + loopback aliases; not connector-dependent) and an **`allowed_origins` policy that fails closed** — server-side connectors omit `Origin` (unaffected), browser origins must be in the validated/canonicalized `MCP_ALLOWED_ORIGINS` allowlist. - Existing installs and PAT-configured users are never broken: their PATs keep working indefinitely (AD1) and remain the active path whenever no live web session exists. *(Amended 2026-07-24 from "no behavior change" — with session-wins precedence, step 2, a signed-in PAT user's requests ride the session; the load-bearing promise is that nothing stops working, not that the credential in use never changes.)*

0. **Build pipeline (new scope — the SDK forces it)**: the extension today has no bundler, no runtime dependencies, and no config layer (`API_URL` is hardcoded to production in `background-core.js`). Clerk's SDK is only consumable as a bare npm import (`@clerk/chrome-extension/client`), which MV3 service workers cannot resolve unbundled — "no React/Plasmo needed" does not mean "no build step." (An earlier draft said `https://tiddly.me` — a transcription error against a correctly-fetched doc; see the external-claims rule.) **Client lifecycle in the MV3 worker** (Chrome suspends and restarts it at will): follow Clerk's documented background pattern — create the client on demand (awaited) when a token is needed — rather than assuming a durable top-level singleton. Coalescing concurrent initializations is optional; if an initialization promise is cached, it must be dropped on rejection (a cached rejection would otherwise poison the worker for its remaining lifetime). **Amendment (2026-07-26, from the first dev sync pass — engineer-approved)**: on-demand-per-request proved user-visibly slow (every popup open paid two sequential Clerk network round trips — status probe, then data calls — and every save a third; a multi-second "Connecting…" on each open). Two bounded optimizations, distinct from the *client* caching the review round rejected: (a) ~~cache the session TOKEN in worker memory and reuse until shortly before its 60-second expiry~~ — **WITHDRAWN in review (2026-07-26), built and then removed the same day**: two reviewers independently rated the wall-clock token cache Critical — in a Sync Host extension it keeps authenticating as a *previous* account for the cache window after an account switch on the web (cross-account data placement, the exact defect class the multi-tenant design exists to prevent), and the original "the web already has this property" justification conflated same-session revocation staleness with new-action *attribution*, which the web does not have. Replaced by **in-flight coalescing of the full token resolution** (client creation + token fetch share one promise per concurrent burst, cleared on settle, no resolved token retained) — a popup open's status/limits/tags burst still costs one Clerk round trip on the snapshot-backed path (a first, snapshot-less open pays a probe and then a data-burst resolution), and every *distinct* interaction re-resolves so sign-in/sign-out/account-switch take effect immediately. Revisit credential caching only with observed latency evidence, and then via a Clerk-supported session-lifecycle signal — never wall-clock TTL, and not speculative cookie-watching; (b) **snapshot the auth mode flags** (`activeMode`/`hasPat`/`hasSession` — never token material) to `chrome.storage.session` after every status resolution, so the popup renders the correct screen instantly from the snapshot and reconciles in the background — "Connecting…" then appears only when no snapshot exists (once per browser session; `storage.session` clears on exit, and the existing `storage` permission covers it). A wrong snapshot cannot lie durably: action-time requests fail with the honest per-credential 401 copy. Implementation home: extract auth (acquisition + coalescing + resolution + status + snapshot) into its own `auth.js` module first — the in-flight resolution promise and snapshot writes are real state the request-handler module shouldn't absorb — and route the worker's thrown not-signed-in errors with a structured `authRequired: true` envelope flag (never prose-matching) so stale-snapshot failures render the signed-out copy, not a generic error.
2. **Token resolution** in the background core becomes (decided 2026-07-24, inverting this step's earlier PAT-first draft — engineer's call after review debate, aligning the mechanism with this milestone's own "PAT stays only as an escape hatch" framing): **a live Clerk session wins; the PAT is a true fallback** — `getToken()` when a session exists; the stored PAT when there is no live session *or the Clerk path fails client-side* (no session, init failure); neither → the existing not-configured error, with copy updated to mention both paths. Fallback happens at **resolution time only**: a server-side rejection (401) of whichever credential was sent is surfaced, never silently retried with the other credential — cross-credential retry would mask real misconfigurations (a broken `azp` allowlist would hide behind PAT retries) and could silently switch which account a save lands in. `X-Request-Source: chrome-extension` unchanged. All resolution lives in **one background-owned resolver** consumed by every API handler; tokens never leave the worker — today's property (tokens don't transit `runtime.onMessage`) is preserved. The popup and options pages learn state via a new `GET_AUTH_STATUS` message returning `{ activeMode: 'pat'|'clerk'|'none', hasPat, hasSession, principal }` — status fields only, never a token (a collapsed single mode can't render the options page's both-configured UI, hence the mode flags). **The `principal` field (added 2026-07-27, owner-scoped caches + request binding)** is an opaque per-account fingerprint (a SHA-256 hash — Clerk: of the token's `sub`, stable across refresh; PAT: of the whole token, credential-scoped by documented design), never a credential. Its contract: it is **never persisted to the snapshot** (the stored snapshot renders the shell only; sensitive content gates exclusively on the LIVE principal), it is accepted only over the sender-validated internal message channel, and it drives two enforcement points — user-derived local caches (`draft`/`draftImmutable`/`defaultTags`/`lastUsedTags`, single-sourced in `cache-ownership.js`) are namespaced per principal so an account switch never surfaces another account's cached data, and every user-data request carries `expectedPrincipal`, which `authedRequest` compares **fail-closed** (missing, null-while-authenticated, or mismatched → structured `principalChanged`, zero network calls) against the principal derived from the same resolution as the credential being sent — closing the render-time/send-time TOCTOU where one account's hydrated draft could be saved under another's session. Legacy pre-namespacing bare-key caches are removed, not migrated (unattributable). The options page additionally resets its in-memory tag state on principal transitions (generation-guarded against late async responses; re-checked on `visibilitychange`). **The popup's mode detection must learn session state too**: today it decides configured-vs-not from `storage.local.token` alone — left as-is, a session-synced user with no PAT would still be shown the old paste-a-token onboarding screen, making M7's headline UX invisible exactly for the new users it exists for; it now consumes `GET_AUTH_STATUS`.

### Implementation Outline

1. **Webhook endpoint — the first inbound provider-calls-us surface in the codebase, treat it accordingly**: a route (e.g. `POST /webhooks/clerk`) that **verifies the Svix signature before doing anything else** — an unauthenticated webhook endpoint is an attacker-triggerable "delete this user" button. The Clerk dashboard subscription is scoped to `user.deleted` only, *and* the handler defensively checks `event.type`, returning 200 no-op for anything else (subscriptions can be broadened later without a code change). Note this is the **first application-level delete-user path** — no service function exists today (`test_user_cascade.py` exercises the ORM cascade directly); M8 writes one, wrapping the tested cascade. Webhooks are sync convenience, never source of truth: JIT provisioning remains the primary path for creation; this endpoint only handles deletion (and is the natural future home for billing/org events).
2. **Deletion must defeat resurrection (review-round Critical finding)**: JIT provisioning will happily re-create a deleted user on the next validly-signed token — a still-live Clerk JWT (a seconds-to-a-day window), or worse, the user's iOS app on the Auth0 path (Auth0 doesn't know a Clerk-side deletion happened, and refresh tokens keep that session alive for the whole M6a→M6b window), producing a resurrected empty row with `external_auth_id` NULL that would also break M6b's `SET NOT NULL` migration months later. The handler therefore: (a) writes a **tombstone** to a new `deleted_identities` table — *both* identity columns when the row exists (`external_auth_id` blocks the Clerk path, `auth0_id` blocks the Auth0/iOS path); for unknown-user events, tombstone the Clerk ID and return success. **Tombstones never block returning users**: providers never reuse identity IDs, so a deleted user who signs up again arrives as a brand-new identity that no tombstone matches — tombstones block dead credentials, not people. **Retention — do NOT add a sweep in M8**: the two tombstone kinds have different required lifetimes. Clerk-side entries are only needed for ~the longest Clerk token lifetime (about a day), but Auth0-side entries must survive the *entire* open-ended dual-accept window — the iOS resurrection they guard against stays live until M6b deletes the Auth0 path. A fixed-retention sweep added now could silently reopen the Critical resurrection hole the moment the window outlives the retention period. The sweep is therefore part of M6b's decommission change-set (see M6b step 4), where it becomes safe by construction, and it goes into the *existing* `tasks/cleanup.py` daily task — no new cron. During the window the table just grows, which at this scale is a handful of rows. (b) **Invalidates the auth cache** for both key segments — the only current `AuthCache.invalidate` caller is the consent flow; deletion is a new caller, without which a cached identity serves requests for up to 5 minutes post-deletion and then 500s on foreign-key violations. (c) Both JIT paths **check the tombstone before create** and reject with a terminal 401 carrying a stable `error_code: "account_deleted"` (with a human-readable `detail`; clients bind to the code, not the prose) — a deliberate exception to the generic-401 policy, safe because only a holder of a validly-signed token for that exact identity can ever see it (M4's friendly `invalid_grant` message is the precedent), and it stops a deleted user's devices looping on an unexplained sign-in failure.
3. **Make the `<UserProfile />` deletion section visible.** This needs no app-side code: the section's visibility is governed **instance-wide** by `user_settings.actions.delete_self` (ledger Q12), a dashboard-only setting that controls the embedded component and the hosted Account Portal together — not an app-gated section M3 hid (M3 relied on the toggle being off). Turn `delete_self` on once the webhook backend is live: on the dev instance for this milestone's manual pass, and on the production instance at M6a (after the production webhook endpoint + signing secret are configured and verified — see M6a pre-flip). The flip branch's `SettingsAccount.tsx` guard-rail comment (which currently notes the toggle is off) gets refreshed to match. (MFA enrollment sections are *not* app-gated either — they simply don't render on a non-Pro instance, Clerk-side; enabling MFA strategies once Pro is active is what makes them appear.)
4. **iOS guide**: one line — deletion and MFA surface via ClerkKit's prebuilt views with the same provider-side semantics; nothing app-specific required.

## Known limitations accepted (recorded, not to be "fixed" in this project)

- Interactive CLI login requires a browser on the CLI's machine; SSH/headless uses PATs (AD9).
- MCP OAuth grants are all-or-nothing (Clerk has no custom OAuth scopes yet) — parity with today's unscoped PATs, no regression.
- One forced re-login per client at its own cutover (web/CLI at M6a; iOS when its update ships). During the M6a→M6b window: Auth0-side password changes do not propagate to Clerk, and users who sign up during the window cannot use the iOS app until it ships.
- Clerk reliability posture: sign-ins depend on Clerk uptime (as with Auth0); networkless JWT verification means existing tokens keep verifying during a Clerk outage, but with ~60s session tokens the practical grace window for web sessions is about a minute. Accepted at current scale; revisit (e.g., tolerating slightly-stale tokens during incidents) only if it bites.
- **Free-tier session policy (DECIDED — adoption register)**: sessions expire on a fixed 7-day absolute lifetime — every active user re-authenticates weekly (one click via Google or a password manager), possibly mid-session, and the expiry propagates to every session-based client: the M7 extension's synced session (fails at bookmark-save moments; the PAT fallback is the escape hatch) and iOS. A knowing regression versus Auth0's 30-day-inactivity default, accepted at beta scale to avoid $300/yr; lifted by the Pro upgrade when the product has real users. The cutover email sets expectations.
- **Account-deletion client teardown is browser-wide, not account-scoped (web) (DECIDED 2026-07-14; active-identity guard added)**: on the terminal `account_deleted` 401, the web client clears the deleted user's local unsynced drafts and BYOK API keys, then signs out and lands on `/account-deleted`. A per-request **active-identity guard** (`frontend/src/services/api.tsx`) ensures the teardown only runs when the deleted identity is still the active session — so a *different, currently-active* account is never signed out or torn down by another account's just-deleted, slow-arriving response. The **residual, accepted** limitation: localStorage is per browser origin (not per account) and drafts/keys are not namespaced by user id, so when the account being deleted is the active one, any OTHER account's *leftover local* drafts/keys in that same browser are cleared too. **Worst case is loss of local unsynced data and locally-stored credentials** (an unsynced draft or a BYOK key may be the only copy, irreversibly erased) — but **never a server-side/account deletion**: no account is deleted and saved/synced data is safe (BYOK keys live only in localStorage; unsynced drafts are in-progress local edits). Full per-account namespacing of drafts/keys is deferred at beta scale (personal, single-account devices). Documented in `frontend/src/utils/drafts.ts` and the `onAccountDeleted` teardown in `frontend/src/components/AuthProvider.tsx`.

## Deferred follow-ups (post-migration)

Work surfaced by the migration but deliberately not part of it — tracked here (rather than a ticket that would get lost) so it survives to be picked up post-cutover.

**Auth-cache post-commit publication** (surfaced by M8's dev drill). Publish auth-cache entries only *after* the request transaction commits — mirroring the deletion path's commit-then-invalidate — so the cache never holds an uncommitted row.

- **Why:** M8's shipped fix (don't cache a user created in the current request) plus the auth-callable guard close the *reachable* phantom-cache path, but a *cosmetic* residual remains: an existing user whose email changed at the IdP has the new email cached pre-commit; a rollback then leaves it stale for ≤5 min (email isn't access-controlling, and it self-heals). This closes it and makes "only cache committed rows" a structural guarantee rather than one that depends on how many times auth runs per request.
- **Shape:** a generic `session.info["post_commit"]` callback list that `get_async_session` runs after `await session.commit()` and drops on rollback; `get_or_create_user` queues the cache write instead of doing it inline.
- **Risk:** medium — it changes `get_async_session` (the shared request-commit path every endpoint uses) and must re-validate the M8 post-populate tombstone recheck and the deletion-side commit-then-invalidate ordering under the new model.
- **Acceptance:** tests exercise a *real* request-end commit boundary (not the savepoint fixtures): same-session double-resolution → rollback → no cache entry; and an HTTP regression (a first-ever user hits a consent-gated route → 451/rollback → consent-exempt provisioning → consent submission succeeds with no foreign-key error). Once landed, the auth-callable guard's phantom-cache rationale dissolves — keep or drop it as a perf/clarity call.
- **Owner:** unassigned.

## Appendix A — MCP OAuth: background and requirements

Self-contained rewrite of an internal tracking ticket (KAN-57) so this public document doesn't depend on private-tracker access. The ticket was originally authored with Auth0 as the authorization server; M5 supersedes those specifics — Clerk plays the authorization-server role. The problem statement, platform facts, and requirements below are unchanged.

### Problem

Tiddly's MCP servers authenticate with bearer tokens (PATs). That works for clients that let users configure headers, but two major platforms cannot use bearer tokens at all — OAuth is their only supported auth for remote MCP servers. Until the servers speak OAuth, those integrations are impossible (ChatGPT) or require a proxy workaround (Claude Desktop via `mcp-remote`).

### Platform compatibility target

| Platform | Auth method |
| --- | --- |
| Claude Desktop / Claude web (native Connectors UI) | OAuth (required for the paste-a-URL experience) |
| ChatGPT | OAuth (mandatory — no bearer option) |
| Claude Code | OAuth or bearer token (`--header`) |
| Codex CLI | OAuth or bearer token (`bearer_token_env_var` / `http_headers`) |

### Requirements

1. Each MCP server serves `/.well-known/oauth-protected-resource` (RFC 9728) — **the only OAuth endpoint we implement**. The identity provider serves everything else: authorization-server metadata (RFC 8414), dynamic client registration (RFC 7591), the authorize and token endpoints.
2. Dynamic client registration is enabled at the identity provider, so MCP clients register themselves — no pre-provisioned client IDs or callback URLs per platform.
3. Existing bearer/PAT auth keeps working unchanged (must-have — Claude Code, Codex, and all current configs rely on it).

### How the OAuth bootstrap works (per the MCP authorization spec)

1. Client sends an unauthenticated request to the MCP server and receives HTTP 401 with a pointer to the resource metadata.
2. Client reads `/.well-known/oauth-protected-resource` from the MCP server, learning where the authorization server is.
3. Client reads the authorization server's metadata, registers itself via DCR (obtaining a `client_id`), and sends the user through browser login/consent.
4. Client attaches the issued token as a bearer on every MCP request; token verification happens server-side exactly as for any other bearer (in Tiddly's architecture: at the backend API, not the MCP proxy — see AD10).

### DCR considerations

- **Pros**: universal client compatibility; best UX (users paste one URL); clients manage their own callback URLs; no manual per-platform client creation.
- **Cons**: open registration (anyone can register a client — spam/abuse surface; this motivated the original concern about Auth0's 10-application free-tier entity limit, and is why M0 verifies how Clerk meters DCR-registered clients); no control over client names/logos; harder to revoke a specific platform; the spec area is still evolving (e.g., Client ID Metadata Documents).

- RFC 9728 (OAuth 2.0 Protected Resource Metadata) · RFC 7591 (Dynamic Client Registration) · RFC 8414 (Authorization Server Metadata)
