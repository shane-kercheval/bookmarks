TL;DR

Tiddly is a multi-tenant SaaS for bookmarks, notes, and prompt templates — a beta with under a hundred users, but an unusually wide auth surface: a React web app, a native iOS app, a Go CLI, a Chrome extension, two MCP servers that let AI agents reach a user's content, plus personal access tokens and deletion webhooks. All of it had to move.

  • Why we moved.
    • AI-agent connectors need dynamic client registration, and Auth0's free tier caps applications at ten — a limit we don't control, since the clients register themselves.
    • Auth0 ships no end-user account UI, so our users had no password change, session management, or account deletion.
    • We were maintaining our own token-refresh code on web and iOS.
    • Clerk's Sync Host lets a browser extension share the web app's session, so the extension needs no sign-in of its own.
  • Trade-offs.
    • On the free tier every user re-authenticates every seven days, versus Auth0's 30-day inactivity window.
    • There is no OAuth device flow, so CLI login from a remote terminal falls back to tokens.
    • Web sessions depend on Clerk about once a minute; a Clerk outage ends them within a minute, where CLI/MCP tokens and PATs keep verifying locally.
  • What we'd ask Clerk to fix, in priority order.
    1. Let API Keys import existing key hashes. Without it, adopting the product invalidates every key your customers already hold — a hard block for anyone with a homegrown token system. The same password_digest pattern already exists for passwords.
    2. Support the OAuth device flow. It's the hardest gap for a CLI-first product; interactive login now requires a browser on the same machine.
    3. Turn on the settings people need, or surface them. Three we required default to OFF and fail quietly (oauth_jwt_access_tokens, pkce_required, Native API), and none of them appear in clerk config pull, so config-as-code can't see them drift.
    4. Reconsider the 7-day free-tier session cap. It's the sharpest downgrade a team feels when moving from Auth0.

Every client resolves to the same internal user record, and the backend verifies tokens itself against Clerk's public keys — no call to Clerk on the request path, which is what makes the outage trade-off what it is.

How the backend dispatches a token

A bm_ prefix routes to PAT validation. Anything else is a JWT routed by issuer, with one Clerk verifier handling two token kinds discriminated by the signature-covered header typ (JWT for session tokens, at+jwt for OAuth access tokens).

What we gained and lost

Two things drove the decision: we couldn't ship AI-agent connectors on Auth0's free-tier application cap, and Auth0 ships no end-user account UI, so our users had no password change, session management, or account deletion. Everything we gained and gave up is below. One rule shaped the scope — the end state had to look as if Clerk had been there from the start, so each candidate feature got an explicit adopt, defer, or decline decision. Billing was the one deliberate defer, until the product charges.

What we did

Agents ran the commands under a show-and-approve policy: every state-changing command was displayed with its reason and approved before running; read-only commands just ran. Inside each step's detail, Human highlighting like this covers exactly what a person did — browser sign-ins, DNS records, dashboard-only settings, store review. Everything outside a highlight was agent-run.

  1. Stood up a dev instanceCreated the Clerk application from the terminal and verified the token shape against a real minted token — claims, lifetime, and which checks actually apply.
    Commands and detail
    clerk auth login
clerk apps create "Tiddly"
clerk apps list
clerk config pull
clerk config schema

    Human The browser sign-in behind clerk auth login — the only non-terminal step here. The schema answered several open questions directly: claim shape, session.allowed_clock_skew (default 5s), session.lifetime (60s, minimum 30), auth_access_control.sign_up_mode.

    Custom claims went in the same way, dry-run first — two config lines replacing what Auth0 needed a deployed post-login Action, namespaced claim names, and env vars for:

    clerk config patch --dry-run ...   # session.claims: email → {{user.primary_email_address}},
clerk config patch ...             #                 email_verified → {{user.email_verified}}

    Then we minted a real session token through the Backend API and verified it with PyJWT against the live JWKS. Two findings shaped the backend: azp is absent on Backend-API tokens, which is where the "present → check, absent → tolerate" rule came from Friction ↓; and a Backend-API user create marks the email verified by default, which an import must override or it will silently vouch for unverified addresses.

    The config itself became the source of truth, normalized and committed, with a diff as the drift check:

    clerk config pull | python3 -c "import json,sys; json.dump(json.load(sys.stdin), sys.stdout, indent=2, sort_keys=True); print()" > clerk/config.dev.json
diff <(clerk config pull | python3 -c "...") clerk/config.dev.json

    With one hole: oauth_application_settings and the Native API toggle aren't in the pulled config at all, so the drift check can't see them. Friction ↓

    clerk api /instance/oauth_application_settings --instance dev

The controls that made it safe

  • Kill switches in the backend, not the provider dashboard. Per-issuer flags controlled whether a first-seen identity could create an account, enforcing the two window rules: the import completes before the first Clerk login, and no new Auth0 identities after the flip. A rejected creation returned a generic 401 and logged the identity and issuer, so a leak through a provider setting is loud rather than a silently created account.
  • Anti-resurrection tombstones. Clerk's hosted Account Portal is provider-rendered — app-side guards can't hide the delete button — so a still-valid token for a deleted account must not silently re-create the user. Deletion writes a tombstone; both creation paths check it and return a terminal 401 with a stable account_deleted code.
  • Nothing irreversible ran for the first time in production. The import and the later consent backfill were both rehearsed against production-shaped data, then re-run to prove they were idempotent.

Where Clerk’s migration guide didn’t fit

The guide is written for large userbases with backend code the team can't change. Two of its central recommendations were wrong for us:

  • Session-token aliasing. The guide suggests emitting {{user.external_id || user.id}} in the session token so your backend can keep keying on old Auth0 IDs indefinitely. If you control your backend, a clean lookup-column swap is simpler and leaves nothing behind. We stored the old Auth0 ID in Clerk's external_id as an audit breadcrumb the application never reads.
  • Trickle migration. The guide suggests running both providers indefinitely and migrating each user the next time they sign in. That exists for userbases too large to move at once; it costs you two live providers, two sets of credentials to reason about, and no clear end date. Importing everyone up front and cutting over once was simpler, and it finished.

What worked

Not capabilities — those are in the table above. This is how Clerk behaved during the work.

  • The CLI and config-as-code — the entire instance config as diffable, committed, secret-free JSON with --dry-run, an agent mode, and a schema command that answered several open questions outright. The only interactive step in the whole setup was one browser login.
  • Ordinary RS256 JWTs — the second issuer, JWKS verifier, azp rule, and cache re-keying dropped into the existing verification path as a parameterization rather than a new stack.
  • PKCE loopback — worked per RFC 8252, and on desktop it beats device flow: the terminal is signed in before the browser tab closes, with no code to retype.
  • Passwordless import — the hosted sign-in never offers a passwordless account a password prompt, going straight to an emailed code, so the cutover email needed one sentence.
  • Popup OAuth for in-place re-auth — worked even under Safari's strictest popup setting, which is what lets us re-authenticate without navigating away.

What didn't work

Each claim below is marked in the source ledger as either exercised against a live instance or read from documentation; the ledger is linked in the appendix.

Product gaps

No OAuth device flow (RFC 8628)

Authorization-code and refresh grants only; device flow is explicitly scoped out of Clerk's own CLI-auth guidance and sits uncommitted on the public roadmap. Without it, interactive login does not work from a remote terminal that has no local browser; those users need a token instead. PKCE + loopback covers the desktop case well.

No import path for existing API keys

Clerk's API Keys product (GA April 2026) is the natural replacement for a homegrown token system — but its create endpoint only generates new secrets. The published API documents no way to import an existing hash, so adoption invalidates every key a customer already holds. Clerk already accepts password_digest on password import, so the pattern exists elsewhere in the product. An import path for existing key hashes would let an established service adopt Clerk without rotating every customer key. Without one, adoption means invalidating keys your customers are already using.

No custom OAuth scopes; no client_credentials

Third-party consent is all-or-nothing, which concentrates all anti-abuse weight on the consent screen's clarity — and that screen displays the client-chosen name, so the registered redirect URI is the only real identity signal. Standards-based M2M is absent (a proprietary token product stands in). Neither affected us — our own tokens are unscoped — but without custom scopes a third-party client gets all-or-nothing access, and without client_credentials there is no standards-based service-to-service option.

Legal consent capture is not version-aware

One legal_accepted_at timestamp — no record of which document versions were accepted, no re-consent trigger on a new version, no enforcement outside the sign-up ceremony. Auth0 has no equivalent feature either (its closest paths are a legacy-widget checkbox that stores nothing, or custom code writing to user metadata), so this is a gap in the category rather than a regression from Auth0. We removed our own version-aware gate for a separate reason — the cross-client enforcement code cost more than the version tracking was worth — and replaced forced re-consent with an email notice. A compliance-heavy product will want version awareness and would have to build it. Related docs gap: the iOS SDK's only legal-acceptance example is a custom flow passing legalAccepted: true — whether the prebuilt UI handles the checkbox is undocumented.

Billing: no refunds, USD only, no VAT, no 3-D Secure

Docs-level findings from a billing evaluation we have not run. The VAT gap alone could be disqualifying for European sales.

Configuration and tooling

Three flags you need on default to OFF

oauth_jwt_access_tokens (instance-level — without it tokens are opaque and networkless backend verification silently breaks), pkce_required (per-application, off on creation), and the Native API setting the extension needs. Discovered one at a time across three milestones, each reproducing identically on dev and prod. A "recommended posture" preset — or JWT tokens on by default — would have erased this whole class.

Why these are easy to miss

The failure modes are quiet: opaque tokens just 401 at a backend expecting JWTs; a missing PKCE requirement doesn't fail at all, it just weakens the deployment. After the second one we started checking for this class of flag before each milestone.

Config-as-code has holes

clerk config pull does not capture the instance's OAuth-application settings or the Native API toggle, and account-deletion visibility (delete_self) is dashboard-only, absent from the config schema entirely. Everything outside the pulled config is invisible to drift detection; those exact settings are where out-of-band drift risk survives.

Enabling DCR force-enables the consent screen — everywhere

Turning on dynamic client registration added a consent screen to all OAuth flows, including the pre-existing first-party CLI login. Arguably the right security default; still a surprising coupling between "let connectors self-register" and an unrelated client's UX, and it cannot be disabled while DCR is on.

The 7-day free-tier session cap

A fixed absolute session lifetime, so every active user re-authenticates weekly regardless of activity — a regression from Auth0's 30-day inactivity default, fixable only with money. It drove real engineering — the in-place re-auth flow and draft autosave exist because of it — and it leaves the CLI holding a longer-lived login than the web app.

allowed_origins updates replace the whole array

Write semantics, not merge semantics: fetch, merge, write — or clobber the origins another client depends on.

clerk deploy and config put silently revert production-only values

Both are whole-instance operations. Some production values legitimately don't exist in the dev config — for us the real Google OAuth credentials and the production Frontend API domain, which Clerk's own model applies on top of the promoted config and which therefore live only on the production instance. Running the documented promotion path a second time, after production has diverged, overwrites those with dev's values. For us that would have meant production Google sign-in breaking, and nothing in the tooling warns you before or after.

We avoided it by making every production change a key-scoped clerk config patch, dry-run first, verified with before/after pulls — a discipline we imposed on ourselves after reading the docs carefully. A diff-and-confirm step on production writes, or a refusal to null out values that exist on the target but not in the incoming file, would close this. It is the CLI's most dangerous behavior and it sits on the happy path.

clerk api reported failure for a create that succeeded

During the production cutover, a clerk api POST creating a user submitted twice: the user was created, then the CLI's own retry hit the duplicate-identifier error and surfaced that as the result. An operator sees a failure for an operation that worked — at the moment they are most likely to react by retrying and least able to afford duplicate identities.

Observed on v1.5.0 and recorded as tool/version behavior rather than a standing property, so it may already be fixed. The rule we adopted holds regardless: after an ambiguous create failure, confirm by listing or retrieving the identifier before retrying, rather than inferring from the call's result.

Docs vs. reality

azp is conditional, and nothing says so plainly

Clerk session tokens carry no audience claim; the equivalent check is azp — but azp is present only on browser-origin tokens. We decoded Backend-API, OAuth, and extension tokens and found it absent; for iOS we have a weaker signal — a production request succeeded with no iOS-specific allowlist entry, so the claim was absent or already allowed, but no iOS token was decoded. A naive blanket requirement (the Auth0 aud habit) would 401 every non-browser client. The correct rule — "present → allowlist check; absent → tolerate" — had to be pinned empirically, token type by token type, by minting and decoding real tokens.

Refresh tokens rotate; the docs say they never expire

Empirically: every refresh returns a new refresh token, replaying a rotated-out one returns invalid_grant, and the replay appears to revoke the whole grant family. Any client storing "the" refresh token instead of always-storing-what-was-returned will strand itself. The never-expire claim remains unverifiable from outside.

Clock-skew leeway is not inherited by independent verifiers

session.allowed_clock_skew (default 5s) governs only Clerk's own validation. A backend doing its own JWT verification — the documented-and-sensible pattern — defaults to zero leeway in most libraries, which under 60-second tokens ships spurious 401s. Passing an explicit leeway fixes it; knowing the argument is needed is the cost.

Backend-API session minting is development-only — discovered mid-cutover

POST /sessions returns request_invalid_for_environment on production instances, so no headless production session token exists. The cutover's planned smoke tests had to be redesigned live around real browser logins and token-free proofs. Documented behavior, but not where someone planning production verification would find it.

The ecosystem is Next.js-first

New features and examples land in Next.js before plain React; the Python SDK is solid but thinner than the JavaScript ones. A Vite SPA + FastAPI backend should expect to hand-roll occasionally. Counterweight: the docs improved during the migration — an official vanilla-JS extension quickstart appeared mid-project and became the reference implementation for the extension work.

Interop & operations

ChatGPT connector onboarding is not self-serve — an OpenAI bug

ChatGPT's DCR registration omits the openid scope its own authorize request then demands. Clerk correctly rejects the mismatch, so every new ChatGPT connector registration is unusable until its scopes are patched — the user sees an instant "There was a problem connecting" bounce before any sign-in renders. OpenAI-acknowledged, open since December 2025. The one-line operator fix (patch openid into the registration) works, but must be repeated per registration. Codex — same company — registers a consistent scope set and works first try, isolating the bug to the ChatGPT connector client.

What this costs Clerk's customers

Clerk is correct to reject the mismatch, but the customer absorbs the cost: the user sees "couldn't connect to your server," and the operator has to watch for new registrations and patch them. Surfacing scope-mismatch rejections in the dashboard, or an opt-in per-client scope rule, would turn a silent support burden into a visible one.

The token endpoint silently 403s default HTTP-library user agents

Bot protection on /oauth/token rejected a default Python-urllib user agent with a bare 403 and no OAuth error body. Cost real debugging time; any CLI or script must set a real User-Agent or hit the same wall with nothing to go on. An OAuth-shaped error response would make this self-diagnosing.

Cloudflare challenges make terminal checks of hosted pages unreliable — in both directions

Clerk-hosted account pages serve bot challenges to non-browser clients as 403s (cf-mitigated: challenge). A curl-based verification that production sign-ups were blocked "passed" for the wrong reason, and the project had to formally correct the finding's provenance and re-verify in a real browser. The rule we adopted: config-level evidence (the public /v1/environment) is trustworthy from a terminal; hosted pages are not.

DCR entity accumulation is real and per-attempt

Registration granularity belongs to the client: one connector add by Claude produced two registrations ~1.5 seconds apart; one operator-day of testing produced seven application records. Cleanup is manual (DELETE /oauth_applications/{id}). Fine at this scale — but registration-endpoint abuse (junk clients, client-name phishing against the consent screen) remains an operational risk the consent screen alone does not mitigate.

Watched, not reproduced: sign-in-initiated SSO sign-up under legal consent

clerk/javascript#8338 describes Google sign-ins that convert to sign-ups failing when legal compliance is enabled. Planned around as a potential launch blocker; on this instance the converted flow rendered the consent step cleanly. The issue is open upstream with an unreleased fix, so this is one instance's behavior, not an all-clear.

What's next

  • Clerk API Keys — the candidate to replace our homegrown token system, gated on the import path above and on the verification model (local, or a call to Clerk per request?).
  • Organizations — when teams reach the roadmap. Clerk supplies the membership layer, prebuilt UI, and self-serve SSO/SCIM at the enterprise tier; the product-side work remains ours.
  • The Pro upgrade — primarily to lift the 7-day session cap; MFA and passkeys come with it. One open question: whether a plan applies per application or per instance.
  • Billing — deferred until the product charges; the refunds, VAT, and 3-D Secure gaps are what to watch.
